# Bruno-Collection (abgeleitet aus `restRequest/`)

Die IntelliJ-HTTP-Requests unter `restRequest/` bleiben der Master (Source of Truth). Diese
Bruno-Collection wird daraus als **OpenCollection YAML** generiert und dient als Alternative zum
IntelliJ HTTP Client sowie zur Automatisierung per CLI und in der CI.

## Struktur

```text
restRequest/bruno/
├── opencollection.yml          # Collection-Root (YAML), inkl. Pre-Request-Script
├── environments/
│   ├── local.yml               # App auf 8081, Auth-Server auf 9000
│   └── k8s.yml                 # NodePorts 30081/30900
├── actuator/                   # aus restRequest/actuator.http
├── authServerRequests/         # aus restRequest/authServerRequests.http
├── openapi/                    # aus restRequest/openapi.http
├── beer-flow-*/                # 1:1 aus den gleichnamigen restRequest-Ordnern
├── beerOrder-flow-*/
├── customer-flow-*/
└── tools/
    ├── http-to-bru.mjs         # Generator .http -> .yml (Default), optional .bru
    ├── package.json            # @usebruno/filestore
    └── package-lock.json
```

Jeder `.http`-Block wird zu einer `.yml`-Datei; Ordner und Reihenfolge (`seq`) entsprechen dem
Master. Flow-Dateien landen im gleichnamigen Ordner, Einzelrequest-Dateien in einem Ordner mit dem
Dateinamen (z. B. `actuator.http` → `actuator/`). Flow-Ordner mit OAuth2 erhalten ein `folder.yml`;
die Requests bleiben auf `auth: inherit`.

## Generierung

```bash
cd restRequest/bruno/tools
npm ci
npm run generate          # node http-to-bru.mjs --source ../..
npm run check             # Exit 1 bei Abweichung
```

Alternativ vom Collection-Root `restRequest/bruno`:

```bash
node tools/http-to-bru.mjs --source ..
node tools/http-to-bru.mjs --source .. --check
```

Nur einen Ordner neu erzeugen:

```bash
node tools/http-to-bru.mjs --source ../beer-flow-list-patch
```

Generierte `.yml`-Dateien tragen den Marker `Generated by tools/http-to-bru.mjs` und werden beim
nächsten Lauf überschrieben. `opencollection.yml` und `environments/*.yml` sind handgepflegt.

## Ausführen

Voraussetzungen: Bruno CLI `4.2.1` (`@usebruno/cli`) und eine laufende App (`:8081`) sowie ein
Auth-Server (`:9000`) – lokal z. B. über `./mvnw spring-boot:run`.

```bash
cd restRequest/bruno

# einzelner Flow
bru run beer-flow-list-patch -r --env local

# alle Requests eines Ordners
bru run actuator -r --env local

# k8s-Profil (NodePorts)
bru run customer-flow-list-patch -r --env k8s
```

Runtime-Variablen (`bru.setVar`) überleben nur einen CLI-Lauf: Ein späterer Flow-Schritt (z. B.
`02-edit-the-created-beer`) kann nicht allein gestartet werden, sondern nur im Flow-Verbund.

## OAuth2

Die Flow-Ordner nutzen OAuth2 Client Credentials (`auth-id`, Scope `message.read message.write`).
Client-ID und Secret kommen aus der Umgebung, nicht aus den `.yml`-Dateien:

```text
BRUNO_CLIENT_ID     → clientId     (Fallback: clientId aus dem Environment)
BRUNO_CLIENT_SECRET → clientSecret (Fallback: "secret" für die lokale Dev-Umgebung)
```

Lokal reicht der Dev-Default. In der CI werden `vars.BRUNO_CLIENT_ID` und
`secrets.BRUNO_CLIENT_SECRET` durchgereicht.

## CI

`.github/workflows/deploy-and-test-cluster.yml` führt nach Helm-Deploy und `helm test` einen
Bruno-Smoke-Test als Pflicht-Gate aus:

1. `actions/setup-node` + `npm install -g @usebruno/cli@4.2.1`
2. Zwei `kubectl port-forward`: App (`spring-6-rest-mvc`, `8081`) und Auth-Server
   (`spring-6-auth-server`, `9000`)
3. Pro Ordner ein isolierter Lauf: `bru run <folder> -r --env local` (Flows, `actuator`, `openapi`);
   `authServerRequests` bleibt eine manuelle Utility-Sammlung (hardcodierte Basic-Credentials).
4. JUnit-/HTML-Report pro Ordner als Artifact `bruno-reports`
5. JUnit-Ergebnisse via `EnricoMi/publish-unit-test-result-action` im Checks-Tab
   (`Bruno API smoke tests`)
6. HTML-Reports werden über GitHub Pages veröffentlicht (Build-Job
   `publish-bruno-report`, Deploy-Job `deploy-bruno-report`)

Schlägt ein Request oder Test fehl, schlägt der Deploy-Job fehl. Die Reports werden trotzdem
hochgeladen und veröffentlicht (`if: always()`); die Port-Forwards werden per `trap` beendet.

### GitHub Pages

Der Build-Job `publish-bruno-report` baut ein `_site` mit `index.html` und den HTML-Reports aller
Ordner und lädt es als Pages-Artefakt hoch. Der separate Deploy-Job `deploy-bruno-report`
(`needs: publish-bruno-report`) veröffentlicht es über die offiziellen Pages-Actions:

<https://dboeckli.github.io/spring-6-rest-mvc/>

Upload und Deploy laufen bewusst in **getrennten Jobs** (offizielles Pages-Muster): dadurch ist der
Upload-Job vollständig abgeschlossen (Artefakt indexiert), bevor `deploy-pages` läuft — das
beseitigt die eventual-consistencybedingte Flakiness des Deploys im selben Job. Ein einfacher
Deploy-Retry (kurze Wartezeit + zweiter Versuch) fängt Rest-Latenz ab, ohne auf interne
Actions-Results-APIs zu setzen.

Einmalige Voraussetzungen:

- **Settings → Pages → Build and deployment → Source: GitHub Actions**.
- Falls das `github-pages`-Environment Branch-Regeln hat: den deployenden Branch erlauben.

Hinweise:

- Es wird immer der **letzte Lauf** veröffentlicht (vorherige Reports werden überschrieben).
- Die Bruno-HTML-Reports laden Vue/Naive UI von `unpkg.com` — der Browser braucht Internetzugang.
- `--reporter-skip-all-headers` entfernt Auth-Header; Request-/Response-Bodies sind weiterhin im
  Report.

## Hinweise

- `restRequest/` bleibt der Master; Änderungen dort erfordern einen neuen Generator-Lauf.
- `node_modules/` und `bru-reports/` sind in `.gitignore` ausgeschlossen.
